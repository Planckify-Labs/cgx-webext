# cgx-webext

A browser-independent implementation of the **WebExtensions** system, so that a browser that has no extension support
(such as [Ladybird](https://github.com/LadybirdBrowser/ladybird)) can run extensions written for Chrome and Firefox.

It is not a fork and not a browser. It is a library, written in Rust with a C ABI, that does everything about extensions
that does not need to know how a particular browser works, and a small, well-defined list of things the browser has to
provide.

> **Status: early, but it runs.** In a Ladybird build with this integration, the "Add to Chrome" button of the Chrome
> Web Store and the "Add to Firefox" button of addons.mozilla.org install extensions (see [docs/STORES.md](docs/STORES.md)),
> and `--load-extension` loads them from files. It runs their background pages, extension pages and content scripts,
> passes messages and storage between them, and gives them the browser's tabs and windows, a toolbar button with badge
> and popup, an extensions panel, context-menu items, keyboard shortcuts and `scripting.executeScript`, and lets them block, redirect and change network
> requests (`declarativeNetRequest`, `webRequest`) and follow navigations (`webNavigation`). **To try it, see
> [docs/RUNNING.md](docs/RUNNING.md).** Progress against the full spec: [docs/specs/webextensions-full-api/tasks.md](docs/specs/webextensions-full-api/tasks.md).

## Why "WebExtensions" and not "translation"?

Chrome and Firefox share one extension model, called WebExtensions: a `manifest.json`, background code, content scripts,
and the `chrome.*` / `browser.*` JavaScript APIs. "Supporting Chrome and Firefox extensions" means implementing that model
once. The project translates nothing between the two browsers' formats; it implements the shared standard and the
differences between the two dialects (Manifest V2/V3, callbacks vs promises, service worker vs event page).

## What works today

All of this is covered by automated tests (`scripts/check.sh`):

| Area | State |
|---|---|
| `manifest.json` parsing for MV2 and MV3, Chrome and Firefox dialects, with diagnostics | done |
| Match patterns, glob matching, content-script selection for a URL, `web_accessible_resources` access checks | done |
| `.crx` (CRX2/CRX3), `.xpi`, `.zip` reading; zip-bomb and path-traversal protection; extension IDs from key/CRX/gecko id | done |
| CRX3 signature check *structure* (the exact signed bytes and key/ID binding); the cryptographic verify is supplied by the browser | done |
| API dispatch with existence, manifest-version, permission and status checks driven by a registry | done |
| `storage.local/sync/session` (with real quotas), `i18n`, `alarms`, `permissions`, `runtime.getURL/getManifest`, lifecycle events | done |
| `tabs`, `windows` from a browser snapshot: `Tab` objects trimmed by permission, `query`, events synthesized by diffing | done |
| `action` / `browserAction` / `pageAction` (badge, title, icon, popup, per tab), `contextMenus` / `menus`, `commands` | done |
| `scripting` (`executeScript`, `insertCSS`, registered content scripts) and Firefox `tabs.executeScript`, with `activeTab` | done |
| `declarativeNetRequest` (static, dynamic and session rules; 100,000 rules match in under 1 ms), `webRequest` with blocking listeners, `webNavigation` | done |
| `chrome.*` (callbacks, `lastError`, MV3 promises) and `browser.*` (promises) JavaScript shim, `onMessage` semantics | done |
| C ABI (`webext.h`) | exercised by a real C program under ASan/UBSan/LSan |
| CMake module | builds the Rust library and links it into a C++23 program, Debug and Release |
| Ladybird patch | applies to a clean checkout at the pinned commit |
| Ladybird integration (toolbar, extensions panel, popups, injection across processes) | built and run in Ladybird |
| **Coverage report** for the whole API surface and for any extension you point it at | done |

What is **not** done yet: service workers as real worker scopes,
`cookies`, the browser-data APIs (`downloads`, `bookmarks`, `history`, ...) and an extensions manager page.
[docs/INTEGRATION.md](docs/INTEGRATION.md) lists each of these with the exact library calls to use.

## How much is supported?

The registry in [`Data/api-support.json`](Data/api-support.json) lists every extension API member Chrome and Firefox have
(availability is synced from MDN's browser-compat-data), and our status for each. The numbers, generated by
`webext-coverage registry`, are in [docs/COVERAGE.md](docs/COVERAGE.md). At the time of writing:

| | members | provided by the core | also counting what the host browser must implement | works in Ladybird today |
|---|---:|---:|---:|---:|
| Chrome | 399 | 93.5% | 94.0% | 86.5% |
| Firefox | 418 | 94.3% | 94.7% | 89.5% |

"Provided by the core" counts what the cgx-webext core implements and tests. Some of those members also need a
browser-side primitive that Ladybird does not have yet (`downloads`, `tts`, `notifications`, `identity`, offscreen
documents, `system.*`, ...): the call is accepted, but it fails or has no visible effect. "Works in Ladybird today" leaves
those out; the full list is under "Waiting for the browser" in [docs/COVERAGE.md](docs/COVERAGE.md), and what comes next
is in [docs/specs/webextensions-full-api/roadmap.md](docs/specs/webextensions-full-api/roadmap.md).

Fifteen popular extensions from both stores have been run in Ladybird (uBlock Origin, uBlock Origin Lite, AdGuard,
Bitwarden, Tampermonkey, Violentmonkey, Stylus, SponsorBlock, Return YouTube Dislike, OneTab, Session Buddy, Read Aloud,
Video DownloadHelper); 13 of them work. See [docs/COMPATIBILITY.md](docs/COMPATIBILITY.md) for each one, and
`Tools/run_extension_suite.py` to run them again.

To see how a specific extension fares:

```console
$ cargo run -p webext-cli -- inspect Tests/Fixtures/mv2-webrequest-blocker some-extension.xpi
Tests/Fixtures/mv2-webrequest-blocker (Request Blocker (MV2) 0.3, MV2)
  verdict: BLOCKED (uses APIs or features that are not supported yet)
  core 17%   with host 67%   (6 distinct APIs/features)
  manifest features:
    [delegated  ] background scripts / event page - host must run a hidden page at the extension origin
    [delegated  ] toolbar action / popup - host UI
    [planned    ] blocking webRequest - needs request interception in the network stack
  APIs used:
    [delegated  ] CF action.setBadgeText (x1)
    [implemented] CF storage.local.get (x1)
    [planned    ] CF webRequest.onBeforeRequest (x1)
  blockers: webRequest.onBeforeRequest, blocking webRequest
```

`CF` shows which browsers have the API. Statuses: **implemented** (the core does it, tested), **partial** (works with
documented limits), **delegated** (the core validates and routes it; the browser implements it), **planned**.

The analysis is a lexical scan of the extension's JavaScript. It follows `const api = browser ?? chrome` aliases and
destructuring but cannot see computed access (`chrome["storage"]`) or APIs reached through a bundled polyfill's
internals. Treat it as a good estimate, not a proof.

## Quick start

```sh
scripts/check.sh                              # fmt, clippy, all tests, ASan run, coverage-doc check
scripts/ladybird-network-test.sh              # the network APIs in a real Ladybird build (needs that build)
cargo run -p webext-cli -- registry           # API coverage tables
cargo run -p webext-cli -- inspect <path>...  # a .crx/.xpi/.zip or an unpacked directory
```

Needs Rust (stable), and for the full check script: Node 22, a C compiler, `zip`, CMake and Ninja.

## Using it in a browser

The library speaks a C ABI ([`crates/webext-ffi/include/webext.h`](crates/webext-ffi/include/webext.h)). A CMake browser
adds it with two lines:

```cmake
add_subdirectory(/path/to/cgx-webext cgx-webext)
target_link_libraries(my_browser PRIVATE WebExt::WebExt)
```

For Ladybird there is a ready-made, opt-in integration: `Integration/ladybird/apply.sh <ladybird-checkout>`. With the
build option off, Ladybird is built exactly as before. See [Integration/README.md](Integration/README.md).

## Layout

```
crates/webext/       The core (safe Rust): manifest, packages, match patterns, permissions, registry, dispatch, storage...
crates/webext-ffi/   C ABI and header; the only crate with `unsafe`
crates/webext-cli/   webext-coverage: registry coverage and extension inspection
Data/                api-support.json - the API registry
Shim/                webext-shim.js - builds chrome.* / browser.* in extension contexts (+ node tests)
Integration/ladybird Patch, adapter and scripts for Ladybird
Tests/Fixtures/      Small extensions used by tests
Tools/               Registry sync/verification against MDN browser-compat-data, real_world.sh (need network)
docs/                Architecture, integration guide, real-world compatibility, generated coverage
```

## Known limits and assumptions

- The **status** of each API is maintained by hand; tests prove that "implemented" entries have handlers and "delegated"
  ones reach the host. Chrome-only APIs that MDN does not document (e.g. `sidePanel`) are also maintained by hand.
- `include_globs` / `exclude_globs` are matched case-insensitively; this is an assumption that should be checked against
  both browsers.
- Match patterns accept an optional port, which Chrome documents; Firefox's handling of ports in patterns has not been
  compared.
- `storage.sync` is stored locally with sync quotas (no cross-device sync); `storage.managed` is always empty.
- Alarms are not persisted across restarts yet.
- The C++ adapter for Ladybird is **type-checked against Ladybird's real headers but has not been linked or run**, because
  that requires a full Ladybird build. Everything on the Rust and C side is executed by tests.

## Security

Extension packages are untrusted input. The reader bounds decompressed sizes, rejects `..`/absolute/backslash paths and
encrypted or ZIP64 entries, checks CRC-32, and caps total size. The FFI layer contains panics. See
[SECURITY.md](SECURITY.md) to report a problem.
